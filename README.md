# Лабораторна робота №3

**Дисципліна:** Технології розроблення серверних компонентів

**Тема:** Інтеграція PostgreSQL, ORM, міграцій, валідації та варіанти бізнес-логіки.

## Опис

Лабораторна робота продовжує ЛР2. REST API для обліку витрат переведено з In-Memory сховища (словників Python) на базу даних PostgreSQL. Тепер дані зберігаються між перезапусками застосунку.

Використані технології:
- Python + FastAPI
- PostgreSQL 16 (запускається через Docker Compose)
- SQLAlchemy (ORM)
- Alembic (міграції)
- Pydantic (валідація вхідних даних і DTO)
- Bruno (тестування API, формат OpenCollection YAML)

## Індивідуальне завдання

У категорії з'явилося поле `user_id`, яке може бути `NULL`:
- `user_id = NULL` — глобальна категорія, її бачать і можуть використовувати всі користувачі;
- `user_id = <id користувача>` — персональна категорія, її може переглядати й вибирати тільки власник.

Що змінилося в маршрутах:
- `POST /category` — у тілі можна передати `user_id`. Без нього створюється глобальна категорія, з ним — персональна.
- `GET /category` — без параметрів повертає тільки глобальні категорії. `GET /category?user_id=X` повертає глобальні категорії та персональні категорії користувача X.
- `GET /category/{category_id}?user_id=X` — новий маршрут. Повертає категорію, якщо вона глобальна або належить користувачу X, інакше 403.
- `POST /record` — якщо категорія персональна і належить іншому користувачу, повертається 403.

Оскільки в проєкті немає автентифікації, користувач визначається за `user_id`, який передається в запиті (у query-параметрі або в тілі запиту). Це спрощена навчальна модель: перевірка доступу працює коректно, але API не перевіряє, що запит справді надіслав цей користувач.

## Запуск проєкту (macOS)

Потрібні Python 3 і запущений Docker Desktop.

```bash
docker compose up -d
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn main:app --reload
```

Після запуску:
- API: http://127.0.0.1:8000
- Swagger: http://127.0.0.1:8000/docs

Під час запуску застосунок сам застосовує міграції Alembic до останньої версії. Їх також можна застосувати вручну:

```bash
alembic upgrade head
```

Параметри підключення беруться зі змінних оточення `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `POSTGRES_HOST`, `POSTGRES_PORT` (або однієї змінної `DATABASE_URL`). Значення за замовчуванням збігаються з `docker-compose.yaml`, тому для локального запуску нічого налаштовувати не потрібно.

## Міграції

Файли міграцій лежать у `alembic/versions/`:
- `0001_create_tables.py` — таблиці `users`, `categories`, `records` із зовнішніми ключами та `ON DELETE CASCADE`;
- `0002_add_category_owner.py` — поле `categories.user_id` для персональних категорій.

Перевірити поточну версію схеми:

```bash
alembic current
```

## Перевірка підключення до БД

```bash
docker compose ps
docker compose exec db psql -U postgres -d expenses -c "\dt"
docker compose exec db psql -U postgres -d expenses -c "SELECT * FROM alembic_version;"
```

Має бути видно таблиці `users`, `categories`, `records`, `alembic_version` і версію `0002`.

## Перевірка збереження даних

1. Створити користувача (`POST /user`) і перевірити `GET /users`.
2. Зупинити FastAPI (Ctrl+C) і запустити знову `uvicorn main:app --reload` — користувач залишився.
3. Видалити і створити заново контейнер БД (volume `pgdata` при цьому зберігається):

```bash
docker compose down
docker compose up -d
```

4. Знову виконати `GET /users` — дані на місці.

Команда `docker compose down -v` видаляє і volume, тобто всі дані.

## Тестування через Bruno

1. Запустити БД і сервер.
2. Відкрити Bruno.
3. Через Open Collection вибрати папку `bruno_collection`.
4. Вибрати середовище Local.
5. Запускати окремі запити через Send або всю колекцію через Runner.

Колекція збережена у форматі OpenCollection YAML (`opencollection.yml` і файли `.yml`). Базовий URL винесено у змінну `baseUrl`. Після створення сутностей їхні id зберігаються у змінні (`userId`, `otherUserId`, `globalCategoryId`, `personalCategoryId`, `otherCategoryId`, `recordId`), тому запити треба виконувати по порядку. Кожен запит перевіряє очікуваний HTTP-статус.

У папці `05 Delete` створені під час тестів дані видаляються, тому колекцію можна запускати повторно.

## Валідація та помилки

Вхідні JSON-дані перевіряються Pydantic-схемами (`schemas.py`), відповіді формуються через окремі DTO (`UserOut`, `CategoryOut`, `RecordOut`).

- 400 `validation_error` — некоректні дані: порожнє ім'я, ім'я не рядком, від'ємна або нечислова сума, більше 2 знаків після коми, неправильний id, невалідний JSON, зайві поля;
- 400 `invalid_request` — `GET /record` без параметрів фільтрації;
- 403 `forbidden` — спроба переглянути або використати чужу персональну категорію;
- 404 `not_found` — користувача, категорію або запис не знайдено.

Суми зберігаються в БД як `Numeric(12, 2)` і повертаються в JSON рядком (наприклад `"250.50"`), щоб не втрачати точність.

## Основні зміни відносно ЛР2

- словники Python замінено на PostgreSQL + SQLAlchemy;
- додано `docker-compose.yaml` з PostgreSQL 16 і volume для даних;
- додано міграції Alembic, які застосовуються автоматично під час запуску;
- додано персональні та глобальні категорії (варіант 2) і маршрут `GET /category/{category_id}`;
- `GET /category` без `user_id` тепер повертає лише глобальні категорії;
- валідацію розширено: обмеження довжини імені, точність суми, заборона зайвих полів, вихідні DTO;
- колекцію Bruno переведено у формат OpenCollection YAML і доповнено тестами варіанту.
